# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Saldo is an offline-first, single-user desktop app for personal/family finances: React + TypeScript + Vite frontend, Tauri 2 + Rust + SQLite (`rusqlite`, bundled) backend. The core idea is low-maintenance tracking: occasional balance updates are enough, with cash flows, transfers, partners, CSV/eKasa import, buckets, assets and tax models layered on top.

## Project rule docs — read before planning or implementing

- `implementation-rules.md` — the authoritative conventions document (data model semantics, money rules, Rust/TS patterns, testing patterns, feature-specific gotchas). Consult it as a constraint reference for any feature work; do not duplicate it here.
- `memory.md` — local, gitignored dated log of what was built and why. Use as context.

- PRDs / business planning docs must not contain implementation details (DDL, structs, file paths, API signatures). Technical/implementation plans should include full technical detail. Plans live in `plans/` (gitignored).
- Edit file contents with the Edit/Write tools, never with shell commands (sed, heredocs, etc.) — a hard constraint from the project's agent instructions.

## Commands

Package manager is **pnpm** (`pnpm-lock.yaml`; Tauri's `beforeDevCommand` runs `pnpm dev`).

```bash
pnpm install
pnpm tauri dev          # full app (Vite on :1420 + Rust backend) on the REAL saldo.db
pnpm tauri dev --config src-tauri/tauri.dev.conf.json   # same, but as com.teamsumbal.saldo.dev with its own saldo.db
pnpm dev                # frontend only — IPC calls fail without the Tauri runtime
pnpm tauri build        # native bundle
pnpm build              # tsc + vite build

pnpm test               # Vitest (jsdom); vite.config.ts excludes tests/** (Playwright) and .claude/** (agent worktrees)
pnpm test src/features/currency/fxRate.test.ts   # single file
pnpm test -t "name"     # filter by test name
pnpm lint               # eslint src/
pnpm format             # prettier --write src/
pnpm run ci             # format:check + lint + vitest + cargo fmt --check + clippy -D warnings + cargo test
                        # (`run` is required: bare `pnpm ci` is pnpm's built-in clean install and wipes node_modules)

cd src-tauri && cargo test                  # Rust unit tests
cd src-tauri && cargo test snapshot         # filter by test name/path substring
cd src-tauri && cargo fmt && cargo clippy -- -D warnings

pnpm test:e2e           # Playwright; requires `pnpm tauri dev` already running at http://localhost:1420
```

- Husky pre-commit runs `lint-staged` (eslint --fix + prettier on staged `src/` files) and then `cargo fmt` + `cargo clippy -- -D warnings`, so clippy warnings block commits.
- E2E specs in `tests/` run against the live dev app and accumulate data across runs (each test uses a unique name prefix).
- Plain `pnpm tauri dev` uses the installed app's identifier (`com.teamsumbal.saldo`), so it opens the same `saldo.db` (or the `db-location.json` folder) and runs pending migrations on it. `src-tauri/tauri.dev.conf.json` swaps in `com.teamsumbal.saldo.dev`, whose app-data folder holds a separate `saldo.db`.
- To prove a change in the running app, use the `verify-saldo` skill (`.claude/skills/verify-saldo/`). It launches the `.dev` identifier inside a `Saldo Dev.app` wrapper, which computer use can target (the plain debug binary has no bundle id), and drives it with computer use.
- `saldo mcp` (the same binary with the argument `mcp`) serves MCP tools on stdio instead of opening the window. It opens the `saldo.db` of the identifier the binary was built with, so a plain `cargo build` binary started with `mcp` opens the real database. Verify it only through `verify-saldo`'s `mcp.sh`, which uses the dev bundle. The `record-invoices` skill (`.claude/skills/record-invoices/`) is how Claude uses it, for invoices and eKasa receipts.
- PDFium (eKasa receipt PDF import) is loaded from a platform library (`pdfium.dll` / `libpdfium.dylib`) placed in `src-tauri/`. It is gitignored and downloaded separately; the platform Tauri configs bundle it as a resource.

## Architecture

### Request path

React page → query/mutation hook → `src/shared/api/index.ts` (thin `invoke('snake_case_command', { input: {...camelCase} })` wrappers) → Tauri command in `src-tauri/src/features/<domain>/commands.rs` → SQL in `repository.rs` (or `repository/*.rs`) → SQLite. Business-critical calculations (snapshots, FX conversion, headline totals, depreciation, tax) live in Rust; the UI renders what commands return.

### Backend (`src-tauri/src/`)

- `features/<domain>/` has `commands.rs` (validate input, build `XxxParams`, call repository), `repository.rs` (all SQL), `models.rs` (serde types), and sometimes pure-logic modules (`tax_models/calculation.rs`, `ekasa/qr_decoder.rs`). `features/mod.rs` glob re-exports every module.
- **Adding a command:** write it in the feature's `commands.rs`, then register it in the `generate_handler![...]` list in `lib.rs`, add a wrapper in `src/shared/api/index.ts`, and update `api-map.md`.
- `AppState` (`lib.rs`) holds a single `Mutex<rusqlite::Connection>`; commands get it via `state.conn()?`. Async commands that do HTTP (OXR FX rates in `oxr.rs`) must lock → read → drop and never hold the guard across `.await` (see `smart_fetch_fx_rates`).
- Errors are `AppError { code, message }` (`error.rs`), serialized to the frontend, where `extractErrorMessage()` turns them into toasts.
- Multi-step writes use savepoints (`with_savepoint` / `with_savepoint_app` in `shared/helpers.rs`). The outermost scope begins `BEGIN IMMEDIATE` and nested scopes are savepoints, and every connection waits up to 5 s for a lock (`db.rs`). Both exist because `saldo mcp` can write to the same file while the app runs.
- **`saldo mcp`:** `main.rs` branches on the `mcp` argument before Tauri starts. `mcp/protocol.rs` is a synchronous JSON-RPC loop, `mcp/tools.rs` is the one tool table (schemas derived from the serde inputs, no SQL), and `mcp/open.rs` opens the DB for each call and refuses instead of migrating, creating a file or falling back. The write tools call `features/entry_batches` (`record_batch`, `undo_batch`, rules in `derive.rs`, which lowers an invoice or a receipt into the `Plan` the one writer takes), which writes through the same `_inner` functions the Tauri commands call. A command is `state.conn()?` plus one call to its `_inner`. A tool that reads files or the network (`read_receipt`) is built with `read_tool_after_outside`, which marks it `openWorldHint` in `tools/list`: its first step gets the `Outside` (PDFium's resource dir, which `run_mcp` takes from the executable's path, and the eKasa API) and no connection, so nothing waits on a file or the network inside a transaction. A write tool never gets `Outside`; `record_batch` checks a receipt against the seal `read_receipt` returned instead of fetching it again.
- **Demo mode** swaps `AppState.db` for a seeded in-memory DB (`demo.rs`) and stashes the real connection in `persistent_db`. Any code path touching the DB works in both modes.
- **Swapping the DB:** every swap of `AppState.db` (demo enter/exit, DB location changes) goes through `AppState::swap_conn` / `replace_conn`, which bump a DB generation. Code that awaits between reading and writing the DB (the OXR fetch) compares the generation before it writes and drops results meant for the other DB. After every successful swap the frontend reloads the window (`reloadAfterDbSwap.ts`), because every cached query and every setting held in component state (the person filter, the theme) belongs to the other DB. The app's mutex does not stop `saldo mcp`, so `relocate_db` takes the old file's write lock before it writes the config and refuses a move when another process wrote since the copy. An MCP write re-resolves the location after it takes its lock and refuses when the file changed.
- **DB location:** `saldo.db` lives in the OS app-data dir unless `db-location.json` there points to a custom folder (`config.rs` `resolve_db_location`). A custom folder without a `saldo.db` falls back to the default in the app and sets `fallback_warning`, so a missing file never becomes a new empty DB. `saldo mcp` refuses in that case instead.
- **Startup:** run migrations, generate due depreciation events, then fetch missing FX rates in the background (only when an `oxr_app_id` setting exists).

### Migrations

`build.rs` scans `../migrations/*.sql`, sorts them, and generates a `MIGRATIONS` const via `include_str!`. Applied state is tracked in `_migrations`. The runner (`migrations.rs`) applies each file with foreign keys off inside one transaction, runs `PRAGMA foreign_key_check`, and records the file in the same transaction, so a migration lands whole or not at all and fails on any orphan row it leaves. To add one, create `migrations/NNN_description.sql` (next number) with no Rust registration needed and no `BEGIN`/`COMMIT` or `PRAGMA foreign_keys` lines, **and** bump the hardcoded migration count asserted in `migrations_apply_cleanly` / `migrations_are_idempotent` in `src-tauri/src/db.rs`. `schema/ddl.sql` is a human-readable reference only, not applied.

### Data model essentials

- `event` is identity/lifecycle (type, account, soft-delete via `deleted_at`). `event_data` is the versioned payload: every edit inserts a new row, and `event.latest_data_id` points at the current one. Always read through `latest_data_id` and filter `deleted_at IS NULL`.
- Event types include `balance_update`, `cashflow`, `transfer` (linked pair across own accounts), and taxable `revenue` / `expense` / `prepaid_expense`. Split groups tie multiple legs together, and bucket links allocate balances to capital buckets.
- **Snapshot balance** for an account at moment D (`transactions/repository/snapshot.rs`) = the latest `balance_update` on or before D, plus the sum of the `BALANCE_FLOW_TYPES` amounts (`cashflow`, `transfer`, `unexplained_difference`) after that balance update and up to D, converted to the consolidation currency with the latest stored FX rate on or before D. `get_accounts_snapshot` takes `asOf`: `live` has no cutoff, so rows and rates dated after today count, while `at` takes a date (read as end of day, `T23:59:59`) or a datetime. An amount whose currency has no rate gets no value and stays out of every total. A rate older than 7 days (31 for custom units) is marked stale, aged from today when live and from the picked day otherwise (`currency/rate_age.rs`).
- **Headline metrics** (Net Worth, Liquid, Total Balance, Left to Spend), their breakdown lines and the rate warnings come back with the same snapshot, built by the pure `transactions/metrics.rs`. Each metric's total is the sum of its counted lines, and every row also appears in it as counted or not counted with a reason.
- **Bucket switch.** `account.bucket_enabled` is a current setting on every bucket, written only by `set_bucket_enabled`, so an account edit never resets it. Off, Left to Spend skips the bucket as `SwitchedOff` at every moment, the other metrics still skip it as an earmark, and it raises no rate warning. Only bucket rows carry `SnapshotRow.bucket` (`BucketState { kind, enabled }`).
- **Income budgets.** `account.bucket_kind = 'income_budget'` marks a bucket whose value is computed and never stored. The value counts only the moment's own month. It is that month's positive cashflows on the person's counted accounts, net of the month's VAT, minus the month's budget (`income_budget_month`), or 0 when the month has no budget. Earlier months never count, so a month's difference leaves the bucket when the next month starts, and Left to Spend takes it in. Counted accounts are the person's `account` rows in the budget's currency that no asset links, and transfers never count. `income_budget::calculation::evaluate` is the one definition; the snapshot row's `balance_minor` and the dialog's `preview_income_budget` both reach it through `repository::evaluate_draft`, and the dialog does no arithmetic of its own. Triggers refuse any event on an income budget, any cashflow tag to one, and a change of a bucket's kind, and `error.rs` turns a trigger refusal into a `VALIDATION` error with the trigger's message. A unique index allows one income budget per person.
- **Checks against the bank app** (`features/bank/`). A `balance_check` stores only what the bank app showed for an own account (`account_type = 'account'`): `bank_balance_minor`, `checked_at` (UTC, in `event.created_at`'s format and clock) and `day` (the user's local day). Whether it matches is derived on every read by `repository::balance_seen_by_check`, the one rule for what a check saw: the account's live balance from today's data, where an event counts with its current version when it was created at or before `checked_at` or is dated before `day`, and a deleted row counts as gone. A card hold counts as it was at the check (`HOLDS_AS_AT_CHECK` in `bank/repository.rs`). A hold an import posted after `checked_at` counts at its amount minus `bank_entry.posting_change_minor`, and a hold an import removed as cancelled after `checked_at` still counts. An entry an import created in a hold's place (`bank_entry.replaces_event_id`: the row that replaced a split hold, or a row, pending or booked, the bank listed again after an import removed its hold) counts only at checks made after it was created, and until then the hold it replaced counts as it was. So an import that posts, cancels or replaces a hold never breaks a check, while a hand delete or edit still does. It and the snapshot splice the same balance SQL from `balance_sql` (`transactions/repository/balance_sql.rs`, which also owns `BALANCE_FLOW_TYPES`), each with its own visibility predicate and `FlowCount` (`AS_STORED` for the snapshot and the causes), so the two cannot drift. Only the account's newest check is read: a live snapshot's own account rows carry `SnapshotRow.verification`, `verified` while it matches, else `differs` with the difference; a picked moment carries none. The snapshot repository never calls the bank feature: `Moment` has a `live` flag set only by `Moment::live`, and the `get_accounts_snapshot` command attaches verifications through `bank::attach_verifications` when it is set. A gap nobody can explain is booked as one `unexplained_difference` event (bank minus Saldo, dated now or at a balance update dated later, no note; it counts at that balance update's moment because it was entered after it, and a balance update entered after the booking replaces it) followed by a matching check. It moves the balance through `BALANCE_FLOW_TYPES`, every reader that filters `event_type = 'cashflow'` (income budget, payments, taxable links) leaves it out, and it can be deleted, not edited. Both writes refuse with `CHECK_CHANGED` when the live balance moved since the user looked. Triggers keep a check on an own account, an unexplained difference a single entry on one, and refuse a second `event_data` row for an unexplained difference. Find the difference lists the likely causes of a gap from `find_difference_causes` (rules in the pure `bank/causes.rs`): only causes whose one fix closes the whole gap (a near-copy, a flipped sign, a row equal to the gap), searched among the counted rows created or edited after the account's newest check, plus an import hint on a CSV-imported account whose newest row is more than 3 days old. A counted unexplained difference equal to the gap's opposite is listed right after the hint whatever its age (a later real row explains it, so the fix deletes the booking), and an unexplained difference is never a near-copy's twin or one of the other kinds. Each fix runs an existing command (`delete_event`, `delete_split_group`, `update_event`) from the dialog, which stays open with the typed bank balance. A change that would turn a ✓ Verified account (its newest check matches) to differs asks first: `update_event`, `delete_event`, `delete_split_group`, `update_transfer`, `create_balance_update` and `bulk_create_balance_updates` run inside `bank::guard_verified_checks`, which runs the write in one savepoint, checks those accounts again and rolls back with `BREAKS_VERIFIED_CHECKS` and the broken checks unless the call passed `allowBreakingChecks`. Their API wrappers take a required `ask` (`useAskToBreakChecks`, whose provider shows the warning above any open modal) and repeat the call with consent; a declined change throws `ChangeDeclined`, which callers swallow without a toast. A note edit or a change on an account that already differs saves without asking, and CSV import never asks (`apply_csv_import` does not run through the guard).
- **CSV import** (`features/csv_import/`). The wizard parses the file and applies the profile's rules in TypeScript, then sends the rows to `preview_csv_import`, which returns a verdict per row and a review token. `apply_csv_import` runs the same pure matcher (`matcher.rs`) again inside one `WriteTxn`, refuses with `IMPORT_CHANGED` when the token no longer matches, and writes every row or none. The token hashes the rows and every entry the matcher read (each with its id, `latest_data_id` and bank entry), so any write to the account since the review refuses, a second apply of the same review included. Matching is one-to-one, tier by tier, and within a tier every candidate pair is ranked by the tier's cost (the same day first, then the closest day), then the row's place in the file, then the entry's id, and taken while both its row and its entry are free (`Claims::take_cheapest` in `matcher.rs`), so the file's order never lets a row take an entry another row of the tier fits better: a row naming own account X takes a transfer leg to X with its day and amount (`inSaldo`) or one with no bank entry, the same amount within 5 days (`transferLeg`); then any row takes an entry with the same day and amount (`inSaldo`); then a row naming no known account takes a transfer leg with no bank entry, the same amount within 5 days (`transferLeg`); then a row naming own account B takes a plain cash flow on B with the opposite amount within 5 days, each the other's only candidate (`completesTransfer`). Everything else is `new`. A transfer leg to X goes only to a row naming no counterpart or X, never to one naming a partner or another account. A row naming an IBAN Saldo does not know (`namesUnknownAccount`, stored with no counterpart) takes a leg to X only when Saldo has no IBAN for X, because the unknown IBAN can be X's but not that of an account whose IBAN Saldo knows. A plain cash flow or a split group matches whatever the row names. An unticked `transferLeg` moves the leg to the row's day and the other leg stays, so each leg keeps its own bank's day. A ticked `completesTransfer` turns the cash flow into the pair's other leg. `bank_entry` holds the export's day, amount and text for each event that a CSV row created or matched. A split group's bank entry sits on its lowest-id leg. An entry's match key is its bank entry when it has one, else its ledger day and amount, so an edited row still matches and a deleted row never does; a card hold shows a pending row and a booked row different keys (below). The review folds the matched rows under a count, and ticking one imports it again. An apply with nothing ticked still records the bank entries and moves claimed legs.
- **Card holds in CSV import.** A profile marks a row as a hold with a `pending_from_column` rule and as a declined payment with `declined_from_column` (each `{ column, pattern }`, a case-insensitive regex, inert when empty or invalid), and maps an optional `card` column whose first masked number (`423473******0501`) is the row's card. Declined rows never leave TypeScript; the review counts them. `bank_entry` keeps one state per bank line (`BankState` in `matcher.rs`, enforced by CHECKs): booked, pending (`hold_seen_to`, the newest row day of the last export that listed it), posted (`posted_at`, `posting_change_minor`, and `held_day` and `held_amount_minor`, the hold's own bank day and amount before the posting) or cancelled (`cancelled_at`, and `cancelled_by_day`, the newest row day of the export that removed it). Two cards fit unless both are known and differ. A hold stays one entry whatever order the exports arrive in and whatever order an export lists its rows, because an entry shows each row one key: a pending row sees it by the day and amount the bank held it at (a pending or removed hold's bank facts, a posted entry's `held_day` and `held_amount_minor`), a booked row by the day and amount the bank booked it at (a booked or posted entry's bank facts), and an entry no import has seen shows both its ledger day and amount. A booked row reaches a pending hold only by posting it. The tiers above gain hold rules, and three of them are not greedy but one assignment each (`take_assignment`, solved by `csv_import/assignment.rs`), because what one row takes decides what is left for another, and no order of greedy tiers can choose between a hold booked at its amount days later and one booked on its day at another amount. An assignment takes the cheapest set of pairs, equally cheap sets told apart by the rows' places in the file and then the entries' ids. The tiers run in this order. The same-day-and-amount tier is an assignment with as many pairs as it can take: an entry in the row's own state costs least (a booked row a booked or posted entry, a pending row a pending hold), then a posted hold a pending row sees by its held day and amount, then an entry no import has seen, then, for a pending row, a hold an import removed (`repository::removed_holds`, part of the review token) that the file is older than, and last a removed hold the file lists again, because only that pair writes. From an export whose newest row is before the hold's `cancelled_by_day` the pair is an `inSaldo` that writes nothing; from one as new or newer the bank lists the hold again, so the row shows as `new` and, ticked, imports a hold whose bank entry `replaces_event_id` the removed one, which then leaves `removed_holds`. A booked row that can be a pending hold's booking at the held amount leaves an entry no import has seen to a later tier, because the hold can be its own; a hold at another amount does not hold it back, because an entry no import has seen on the row's day and amount is likelier the booking itself, recorded before Saldo kept bank facts. Next, the booked rows still new are paired with the unused pending holds, and only the pairs at the held amount are kept. Then one assignment pairs the rest with the unused pending holds and with the holds an import removed when the file is as new as the export that removed them or newer. So a removed hold never takes a booking a live hold of its amount explains, a booking takes a removed hold of its amount over a live hold at another amount when that costs less, and at an equal cost the live hold wins. Then come the near-legs tier and the booked rows still new taking an entry no import has seen on their day and amount. Last, after the cash flow tier, the pending rows still new are paired with the unused entries a newer export booked. `pair_cost` says whether a booking can be a hold's and what the pair costs, in basis points of the held amount: at the held amount on the held day or up to 5 days after it, 1,000 a day, or on the held day at another amount of the same sign when both cards are known and equal, the gap from the held amount, in either case less than `PAIR_WORTH` (6,000, a booking 6 days after its hold), so a booking at another amount pairs only when it is less than 60 % away. So a booking on the hold's own day less than 10 % away costs less than one at the held amount a day later. A hold that names a card is a purchase on that card, so only a booking that names the same card can be its booking, from either side: a booked row with no card never posts a hold with one, and an older export's pending row with a card never finds a booking without it. A hold with no card (a profile without a card column) takes a booking with or without one. The two hold stages take the cheapest set of pairs, a pair only while it costs less than leaving its hold and its booking unexplained (`PAIR_WORTH`), so a move of other bookings to farther holds pairs one more only when the whole move costs less than that. Then they pair every further live hold with a booking at its amount that they can without moving a pair at another amount or with a removed hold (`sure` edges in `assignment.rs`), because a run of one card's holds of one amount, each booked up to 5 days later, is one booking each however far the run spans. A pair at the held amount is `holdPosted`. One at another amount is `holdPostedAtOtherAmount` (shown among the new rows, ticked; `CsvImportResult.repricedHolds` counts the ones posted). A pair with a removed hold shows as `new` and, ticked, imports the row as a new entry posted from that hold (`replaces_event_id` the hold), so a check made while the hold was pending or after it was removed stays verified. When the hold at another amount is a split group, Saldo does not rework the split: the row is `newReplacingSplitHold`, shown among the new rows, ticked, with a warning that the user can split it again. Ticked, it creates the row's entries as `new` does (the review's split and bucket choices apply), soft-deletes the split hold as a whole without `cancelled_at`, and records the new entry's bank entry as posted from the hold (`held_day` and `held_amount_minor` from the hold's bank facts, `posting_change_minor` the new total minus the hold's, `replaces_event_id` the hold). `repricedHolds` counts the hold and `imported` the entries. Unticked, the hold stays pending and the row imports nothing. The hold is never listed as cancelled. The last stage sees a booking from the pending row's side: a booked or posted entry at the row's amount on its day or up to 5 days after it (a posting Saldo made from another day's hold included), or a booked entry, never a posted one, on the row's day at another amount. Those are `inSaldo` and write nothing. When the bank's data fits two stories with the same end balance, the cost picks one, and Saldo cannot do better: a hold H and two booked rows on its card, X on H's day less than 10 % from H's amount and Y at H's amount a day or more later, is H repriced to X and Y another purchase, or H booked as Y and X another purchase, and Saldo takes the first; a hold the bank cancelled and a purchase no export listed pending, booked on its day and card less than 60 % from it, is a cancelled hold and a new purchase, or the hold repriced, and Saldo takes the second. Either way the balance is the bank's, and only which entry carries which purchase can differ. Posting updates the entry in place through `update_event` and keeps its date, bucket, partner and links, so a check that counted the hold by its day still counts it. The entry takes the row's amount when it differs and the note from `Recorded::note_once_booked`, which is the booked text while the note is the bank's text or a card hold's text. A card hold's text has Tatra banka's layout (`is_card_hold_text`: 40 characters, a run of 3 spaces inside, two capital letters at the end), because a booked row's own text can carry 3 spaces too (`HTTP   M EKOLKY GOV SK`). A split hold's legs keep their dates and the group takes the note. A booked row matched as `inSaldo` never changes the note of an entry with bank facts, and replaces only a card hold's text on an entry no import has seen (`Recorded::note_once_seen_booked`). A ticked `holdPosted` row imports as a new entry and raises the hold's `hold_seen_to` to the file's newest row day, so only a newer export can cancel the hold. An unused pending hold on a day the file covers, in a file whose newest row is after its `hold_seen_to`, is a cancelled hold: `preview_csv_import` lists it, `apply_csv_import` takes one `{ eventId, remove }` per listed hold and soft-deletes the ticked ones. A transfer leg is never a cancelled hold. `csv_import/tests/export_sequences.rs` replays random purchases and exports in order, out of order and with a check between imports, and `adv_sequences.rs` adds purchases made after the day's export, reprices on holds that share their card and day, splits and the user's edits, holds booked up to 5 days after their day, and holds the bank lists on their day, then nowhere until it lists the booking. It checks that every posted entry pairs a hold and a booking of one purchase, and that an older export imported after a newer one adds at most the purchases the newer one no longer lists. The drop-out runs assert a check only right after it is made, because a dropped hold's booking can post another hold of its card and amount, and the data of that day fits both stories with the same balance. Every run must end where the bank does; a seed that fails only because the bank's data fits two stories is left out by number with the story. They replay seeds 1 to 399; `SALDO_HARNESS_SEEDS=2400` replays 1 to 2400, and `887-887` one seed.
- **Tax models are a yearly forecast.** A model stores the month its actual figures cover, a monthly payroll amount, values the user typed per line, profit left from earlier years and minimum tax bands. Each of the five lines (revenue, payroll, depreciation, deductible and non-deductible costs) takes the typed value when there is one. Otherwise it follows its rule in `LineSpec::of` (`tax_models/forecast.rs`), which uses the person's revenue and expense entries, the asset's depreciation schedule, the average of the actual months, or the payroll amount. Depreciation follows its schedule, and a prepaid expense's yearly share and an asset's lost VAT entry count once in the month they are dated, never averaged. A typed year-so-far is taken from the accountant's books, so the depreciation schedule's months so far leave it before it is averaged, and only prepaid shares and the schedule dated after it are added to that average. An asset written off at once is a plain expense. A company's bracket and minimum tax are picked by revenue, a physical person's bracket by the tax base, and a bracket's upper bound belongs to that bracket.
- **An asset's purchase and business use:** `split_purchase` (`assets/purchase.rs`) is the one table that turns a price with VAT, the reclaimed VAT share and the business use at purchase into what depreciates, the lost VAT entry and the dashboard start value. `purchase_price_minor` stays the amount that depreciates, and VAT facts own it once they exist. `asset_entries` (`assets/schedule.rs`) is the pure list of an asset's system entries, so startup and a recalculation write the same rows. A month takes the share of the latest `asset_business_use_change` at or before it, else the share at purchase. `event.asset_entry` tells depreciation from lost VAT, because one month can hold both. `store_use_terms` is the only writer of these columns and stores 100 % as NULL, so `get_use_terms` reads a plain asset for an untouched one. Only `entry_batches/repository.rs` also reads them directly, to compare an asset with its batch snapshot. `resolve_purchase` (`assets/resolve.rs`) decides which terms and price an account save takes, and a new asset with VAT facts starts at `start_value_minor` on its purchase date unless the user typed an initial value. An account update that leaves out `asset_use` keeps what is stored, unless it clears the price or the date, which clears the terms too. Editing the terms later does not move the asset's balance.
- **Private use:** `event_data.private_use` marks an expense that is also used privately. When some VAT really comes back, `split_expense_cost` keeps the lost VAT out of the deductible base, and a prepaid expense puts it in one extra child at 0 % deductible. With no VAT coming back the switch changes nothing, and the forms and `saldo mcp` both store it off on a line with no lost VAT. The field is required on every wire input, so a form or a batch that drops it fails instead of resetting the entry.
- **Where an entry came from:** `event.source_ref` (and `account.source_ref` for an asset) holds one prefixed reference built only by `SourceRef`: `online:` and `offline:` for eKasa receipts (built from a parsed `ReceiptCode`, the same in the app's import and in `saldo mcp`), `invoice:<ISSUER>/<NUMBER>` for invoices recorded through `saldo mcp`. It is not unique, because split legs share it and the app's import lets a receipt be imported twice on purpose (`saldo mcp` refuses a second one). `find_recorded_source` decides "already recorded" from live rows. `entry_batch` records each MCP batch, and `batch_id` marks its entries, split legs, asset accounts and their starting balance. Prepaid shares and depreciation are found through their links.
- **eKasa:** `ekasa/reading.rs` is the one file-to-receipt reader (QR decode, the Finančná správa fetch, lines grouped by name and VAT rate) for the wizard and `saldo mcp`, and both get its `ReceiptReading` as is, plus whether the receipt is already in Saldo. It always decodes the file first; an online id Claude typed counts only when the QR code does not decode. `ekasa/rules.rs` is the one rule matcher (case-insensitive regex, accents ignored on both sides, first match wins); the wizard reaches it through the pure `match_ekasa_rules` command because it matches unsaved rules, sends only the patterns, and copies the matched row's percentages as typed. The wizard falls back to the profile's Default row; `saldo mcp` falls back to Claude's own judgment, and a share the user dictated beats a rule.
- Money is integer minor units (`i64`). Percentages are integer basis points (10000 = 100%). Datetimes are local ISO strings `YYYY-MM-DDTHH:MM:SS`.

### Frontend (`src/`)

- `app/router.ts`: TanStack Router with **memory history** (no URLs; `/` redirects to `/dashboard`). Route components are zero-prop and self-fetching, because props on a route component are silently `undefined`. The ledger route takes an optional `accountId` search parameter, which a dashboard card's "View in ledger" sets and `useLedgerData` reads once as its first account filter. A link that marks the current page (the sidebar) sets `includeSearch: false`, or a route with a search parameter shows no page as current.
- The pages scroll inside the shell's `<main>`, not the window. `app/useScrollTopOnPathChange.ts` sets its `scrollTop` to 0 on the next animation frame when the path changes, and the sticky `Header` stays at its top. The card around the page clips with `overflow-clip`, because `overflow-hidden` would stop the header from sticking.
- `shared/ui/ConfirmDialog` takes a required `action`: `delete` (red "Delete" button, "Confirm deletion" title), `confirm`, or `breakChecks` (the verified-check warning, whose "Change anyway" stays disabled for 600 ms so a double-click on the button beneath cannot answer it).
- `app/App.tsx` is the shell (Sidebar/Header/`<Outlet />`/Toaster) wrapping the providers: `ModalProvider`, `TimeMachineProvider` (the dashboard's `asOf`, live until a date is picked), `SelectedPersonProvider`, `DemoProvider`, etc. Each context is split into `useXxx.ts` (context + hook) and `XxxContext.tsx` (provider only) for Vite Fast Refresh.
- **Modals** are driven by a single `ModalState` discriminated union (`shared/types`). Pages call `useModal().setModalState({ type: ... })`, `app/AppModals.tsx` renders the matching modal, and `app/useModalActions.ts` holds the shared mutation handlers.
- **Server state:** TanStack Query singleton in `app/queryClient.ts` (`staleTime: Infinity`, no refetch on focus, global error toast). Refresh after mutations only via `queryClient.invalidateQueries` with key prefixes (`['snapshot']`, `['events']`, `['persons']`, ...). Shared query hooks are in `shared/hooks/`. The one exception is `app/useRefreshOnExternalWrites.ts`: when the window regains focus and `PRAGMA data_version` moved (another process such as `saldo mcp` wrote), it invalidates every query.
- `features/<domain>/` holds pages, modals and hooks per domain. Do not import across unrelated features; promote shared pieces to `shared/` (`ui/` holds the shadcn/Radix primitives and app-specific inputs).
- i18n: i18next with YAML locales `src/i18n/locales/en.yml` and `sk.yml`. Add every new key to both.
- Use the `@/` alias for `src/`.

### Conventions most often relevant (details in `implementation-rules.md`)

- Display money only through `<NumberValue>`. Convert with `toMinorUnits` / `fromMinorUnits`, and use `<CurrencyInput>`, `<PercentageInput>` and `<DatePicker>` for those input kinds.
- Rust: no SQL in `commands.rs`. Repository functions with 2+ params take a `pub struct XxxParams` (owned fields, `Default` where useful). Use `div_round` for proportional money splits and floor division for tax rates.
- TS: components and hooks are `const` arrow functions (ESLint-enforced), with no explicit JSX return types. A `.tsx` file exports only components. A component that grows sub-components becomes a folder `Foo/` with `Foo.tsx` plus a pure barrel `index.ts`, and the flat `Foo.tsx` is deleted.
- Radix `<Select>` item values must never be `""`. Use sentinels like `"none"` / `"all"`.
- Vitest: wrap components and hooks using queries in a fresh `QueryClientProvider` per test. `vi.mock` factories that need TanStack Router must be `async` and use `await import(...)`. See `src/app/App.test.tsx` for the app-level `createTestRouter()` / `renderApp()` pattern.
